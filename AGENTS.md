# Repository instructions

## Scope

SpecAMQP holds a **specification**, not an implementation. The deliverable is a
complete, correct, executable formal specification of AMQP 1.0 core (OASIS
Standard, Parts 0–5) in Lean 4, with a clause-level ledger that makes completeness
and fidelity measurable. Read `PLAN.md`; it is the programme of record.

There is no Rust, no extraction, no Charon/Aeneas and no performance work here.
Those belong to TemperMint and are scheduled there; `PLAN.md` §23 records what
downstream work needs from this repository.

## Layers

- `spec/oasis/` — vendored OASIS artifacts and their notice. **Immutable.** Byte
  identity is pinned in `toolchain/sources.toml`. Never edit; `scripts/fetch-oasis.sh`
  refuses a mismatch, and every clause id, disposition and vector citation refers
  to these bytes.
- `ledger/` — the clause ledger and its coverage report (generated), dispositions
  and the ambiguity register (planner-authored), and the baseline reconciliation.
- `lean/Generated/Oasis/` — the declared surface as Lean data, generated by
  `scripts/gen-oasis-lean.py`. **Generated; never hand-edited.**
- `lean/Spec/` — the handwritten semantics (executable, total, independent of
  every consumer).
- `lean/Contracts/` — acceptance declarations for every specification claim.
- `lean/Proofs/` — proofs.
- `scripts/` — generators, the ledger, and the fetch/verify script.
- `tests/contracts/` — the observable contracts; `fixtures/` holds planted
  controls, never evidence.
- `vectors/` — specification test vectors (positive, negative, recorded
  third-party) and their schema.

## Contract ownership

Planner-owned; coders and reviewers must not modify them, and a changed file
requires an explicit planner update plus a regenerated SHA-1 manifest:

- `toolchain/sources.toml`
- everything under `ledger/` (ledger output included: it is generated, but its
  content is the reviewed record)
- `tests/contracts/**` including fixtures
- `lean/Spec/**`, `lean/Contracts/**`
- `vectors/**` once a vector is committed as contract

Coder-owned: `flake.nix`, `flake.lock`, `scripts/**`, `lean/Proofs/**`,
`lean/Generated/**` (regenerated only), `AGENTS.md` under planner review.

## Commits

- **The workspace's git index is shared between agents.** `git add <paths>` does not
  protect a commit from another slice's staged entries: an explicit-paths commit still
  commits whatever is already staged, and one session's nineteen-file commit went out
  under a message describing three of them. So stage and commit in one command, never
  leave a staged set sitting while you do something else, and when a commit does come out
  describing more than it names, amend the message rather than the record — a log nobody
  can audit is worse than a message admitting a sweep.

- **Commit only the paths your slice owns**: `git add <paths>`, never
  `git add -A` or `git add .`. Parallel slices have uncommitted work in the tree
  by design, and a pathspec-free add commits whatever state it finds — a
  half-written file of someone else's slice under a message describing your own
  change. This is not hypothetical: commit `ebf7d33` did exactly that, sweeping an
  intermediate `lean/Ref/Value.lean` (whose map-pair writer did not yet compile)
  into a commit about the ledger gate, and it took a corrective commit to undo.
- A coder may commit its own slice's files and must report the commit id; a
  planner pass that rewrites planner-owned files commits those files only.

## Test forms

- **Specification properties and invariants** are theorem or
  interface-conformance contracts, not Given/When/Then: they are mathematics over
  a defined domain.
- **Vector replay, mutation and refusal tiers** are BDD scenarios at the harness
  boundary. The actor is the operator running the driver over a corpus; the
  observable outcome is the verdict report, the named error condition and the exit
  status, and those are contract rather than incidental log wording.
- **Ledger, schema and provenance checks** are data/workflow contracts. They run
  as plain shell contracts (`tests/contracts/*.sh`) today; `.feature` contracts
  (from the V-tier corpus work onward) will be driven by a `scripts/run-contracts.py`
  adapted from TemperMint's runner, added with the first feature contract rather
  than in advance.
- **Generators are contracts too**: a generator must reproduce its committed
  output byte-for-byte, and a mutation of its input must change that output.

## Rules that keep the evidence meaningful

- **No test may call a network service, a model, a real clock or randomness.**
  Third-party capture is a manual, off-gate activity whose *outputs* are
  committed; replay is offline. Generated inputs use committed seeds.
- **Vectors are authored from clauses or recordings, never produced by the
  executable specification.**
- **Generated tables are data, not semantics**: semantics are handwritten, and
  no file under `lean/Spec`, `lean/Contracts` or `lean/Proofs` may contain a
  literal descriptor code or an `amqp:`-shaped symbol.
- **Failure first**: every new contract is run and observed failing before the
  implementation that satisfies it, with the exact command and diagnostic
  recorded. A test never observed to fail protects nothing.
- **No `sorry`, no `noncomputable`, no unreviewed trust**: the proof-integrity
  and executability gates are part of acceptance, and `native_decide` requires
  explicit disclosure because it adds trust.
- **Experiments belong outside the library trees.** A scratch module dropped into
  `lean/Proofs/` or any other library directory sits inside that library's glob: it is
  compiled by `lake build`, scanned by the trust gate, and, if committed, shipped as
  part of the specification. One landed there this session and printed during every
  build until it was removed. Use `/tmp`, which can still `import` the project's
  modules.
- **A build whose result is evidence sets `LAKE_NO_CACHE=1`.** Without it `lake`
  may use mathlib's cache hook and fetch over the network into the provisioned
  workspace, so the build can rest on artifacts that arrived over the wire rather
  than on what the pinned closure provides. Every contract script already does
  this; an ad-hoc verification build must too. A build that did not is disclosed
  rather than counted, which is what happened once in this repository — the
  conclusion drawn from it was re-derived from an offline build before being
  relied on.

## Commands

Everything runs in the pinned shell; the first `nix develop` realizes the closure
and every later run is offline.

```sh
alias shell='nix --extra-experimental-features "nix-command flakes" develop --offline --no-update-lock-file .#spec --command'

shell bash tests/contracts/s0_sources_ledger.sh      # vendored identity, ledger, dispositions
shell bash tests/contracts/s0_tables_fidelity.sh     # generated tables current and load-bearing
shell bash tests/contracts/s0_lean_environment.sh    # pinned toolchain, mathlib, offline resolution

shell python3 scripts/clause-ledger.py check         # ledger + audit + reconciliation
shell python3 scripts/gen-oasis-lean.py --check      # generated tables current
shell python3 scripts/gen-oasis-lean.py              # regenerate after an artifact change (never edit by hand)
```

`scripts/fetch-oasis.sh --verify` checks the vendored bytes offline;
`scripts/fetch-oasis.sh` (without `--verify`) is the only step that fetches, and
it refuses any hash mismatch.

## Environment

The `spec` shell provisions a writable copy of the pinned mathlib closure into
the gitignored `lean/.lake` from the prewarmed store path named by
`SPECAMQP_LEAN_WORKSPACE`, reusing it while its marker matches. Lean and mathlib
are pinned to exactly the revisions TemperMint pins, so a module proved here can
be required by downstream proofs with no version surgery;
`s0_lean_environment.sh` checks that agreement rather than trusting it.
