## 1. What changed

`flake.nix` is the functional change; this status file is its evidence — two files in the commit, nothing else.

The `spec` shell now installs a low-priority Lean shim, with `SPECAMQP_LEAN_NICE=0` as the only opt-out:

- **Two wrappers** in a temporary `specamqp-lean-nice` directory prepended to `PATH`, each of the form `exec nice -n 19 <path> "$@"`. The target is written from `${leanDistribution}/bin/{lake,lean}` — an absolute pinned store path, **never** the result of a `command -v` lookup. A lookup can return an exported shell function's name or an unrelated host tool of the same name, and a wrapper built from that re-enters itself instead of reaching the pinned binary.
- **Two shell functions**, `lake` and `lean`, running the same absolute targets under `nice -n 19`. In bash a function beats a `PATH` entry, so without them an inherited `lake` function would shadow the shim and silently run an unniced, possibly unrelated tool. Their export attribute is cleared with `export -n` after definition: redefining an imported exported function otherwise keeps that attribute, which hands the function to every child shell, whereas clearing it leaves child processes resolving through the shim.
- **All-or-nothing installation.** If the directory or either wrapper cannot be written, the shell reports exactly what failed and exits non-zero — interactive shells included, since an unshimmed Lean is not the state this shell promises and `SPECAMQP_LEAN_NICE=0` exists to make that state deliberate.

Why: Lean elaborates with every core it can find, and on a workstation that starves the desktop's audio and editors for minutes at a time. This is environment ergonomics, not specification work — no artifact, contract, ledger, vector, proof, pin or lock is touched.

## 2. Why it applies to non-interactive commands too

Classification is per repository and rests on that repository's evidence contract, not on interactivity as a proxy. Nothing in this repository compares a recorded environment:

- `s0_lean_environment.sh` reads `lean --version` (the pinned `4.31.0`) and the shell's declared `SPECAMQP_LEAN_TOOLCHAIN`; its `command -v` calls are existence checks.
- `s0_spec_manifest.sh` hashes planner-owned file bytes.
- No contract or script performs a store-path equality, `readlink` or `realpath` comparison, and none records a process environment. (An independent reviewer searched all of `tests/contracts/`, `scripts/`, `lean/lake-manifest.json` and `toolchain/` for exactly this and found none.)

Each of those readings is unchanged because the wrapper execs an absolute pinned store path, so the shim applies to every command the shell runs — including the `shell` alias form and therefore agent-driven and automated builds, which are the long ones.

The contrast is deliberate: TemperMint stays **interactive-only**, because its accepted certificate path records and compares the build environment verbatim and its frozen acceptance commands do not predeclare an opt-out before shell entry. Broad is right here and narrow is right there, for evidence-contract reasons in both cases.

## 4. What this does not establish

- **No timing or performance claim whatsoever.** Niceness is scheduling priority, not throughput; this repository carries no timing evidence and this change alters none.
- **Provenance of the manifest failure is not proved by the mtime.** The file's mtime shows it was written before this commit; that it belongs to another slice rests on the assignment context identifying the concurrent work, not on the timestamp. What the evidence does establish is that the failure is independent of the shim.
- **The failure-branch row is a code-level exercise, not a real `nix develop` run.** The nix-provided shell supplies its own `TMPDIR`, so forcing that path inside the real dev shell would need a read-only filesystem; the row reports the hook's own source text run under bash instead.
- **The function definitions reach only the shell this hook creates.** They take effect in the dev shell itself and are cleared of their export attribute, so child processes — including anything `--command` spawns and any script those children run — resolve `lake`/`lean` through the `PATH` shim instead. A shell function still shadows a `PATH` entry in any *other* shell, and this hook cannot change that.
- Nothing here changes how another repository's shell resolves its tools, and nothing advances or blocks a `PLAN.md` milestone.
