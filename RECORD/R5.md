## The demonstration server — scope, revised after review

**Goal.** A server demonstrating the three properties this repository has together and nothing else in this space has: a ledger in which every clause's status is measured, a second independent reading that catches the first one's misreadings, and an implementation proved to conform to the first. The gates remain the evidence; the demo is a presentation of them.

**Shape chosen: sequential.** A client subscribes and detaches, another publishes, the first reconnects and fetches. This is chosen rather than recommended, and its consequence is stated: **the first demo shows no live fan-out**, because the shipped shell serves one connection at a time (`Shell.Driver.serveConn` accepts once, `:318-327`) and that synchronous shape is a property this repository states deliberately. Competing consumers on one queue are demonstrable sequentially; a topic fanning out to two connected subscribers is not, and demonstrating it would mean concurrency in the shell with a new unproved surface beside the socket boundary and the loop. A demo is not worth widening the trust base for.

**The seam must carry application state, and this is a change to the shell rather than a detail.** `App` is `State → List Output → Reply` (`Shell/Driver.lean:126`), `runConnection` always begins from `Impl.Core.initial` (`:301-306`), and `serveConn` returns only the core's `State` for one connection (`:318-327`) — so no application state is passed in or returned, and a queue cannot retain a subscription or an event across a reconnect. The seam therefore widens to thread application state — `σ → State → List Output → σ × Reply` — with `σ = Unit` at every existing call site. **`σ = Unit` preserves R4's observable wire behaviour, not its source**: `App` is currently `State → List Output → Reply` and every implementation is a two-argument lambda returning a `Reply` — `scripts/endpoint/WireApp/Main.lean:133`, `scripts/endpoint/EndpointProbe/Client.lean:56,67`, `Shell/Main.lean:43,53` — while `runConnection`, `serveConn` and `dial` (`Shell/Driver.lean:301-334`) take and return only the core's state. The widening is therefore a **migration**: each `App` implementation is edited to take `Unit` and return the pair, each lifecycle call site threads it, and the initial and final state handling is written out rather than implied. What survives is the behaviour, and that is measured rather than argued — `tests/contracts/r4_wire_differential.sh` passes after the migration with the same per-vector report it gives today, and its report contract is retained as it stands. **State lifetime is the process**: in-memory, gone at exit, and that is what "no persistence" means here — no durability across restarts, not no memory. The unproved surface this adds is the node dispatcher and the widened seam, both in the tree this repository already declares unproved (`lean/Shell/` and the application directory), and the boundary count the trust gate prints stays where it is because no new `@[extern]` appears.

**The messages are AMQP's own, and the application format is not this repository's.** **Superseded by §23.4**: the demo's messages are the message layer this repository already specifies — Part 3, the 37 clauses S5 still owes — and its body is a `data` section. CloudEvents is a specification *above* AMQP and moves to the repository that owns the application, which is where the rule in §23.3 puts it. Correctly stated: in **structured** mode the event attributes and data go in the message's application-data section, and support for the JSON event format is required *of an implementation that supports structured mode* — not unconditionally. In **binary** mode the attribute values other than `datacontenttype` go in the **`application-properties`** section under a `cloudEvents:` prefix, with `datacontenttype` mapped to the AMQP `content-type` property. The binding defers attribute definitions and the structured event representation to two further specifications, so the demo's dependency is **three pinned documents** — the binding, the CloudEvents core specification, and the JSON event format — each fetched and byte-identity pinned the way `spec/oasis/` is, and each cited by id rather than paraphrased into the codec. The binding's own scope statement is the seam that keeps the pair coherent: *"this specification does not prescribe rules constraining transfer or settlement of event messages with AMQP; it solely defines how CloudEvents are expressed as AMQP 1.0 messages."*

**Deliverables.** (D1) The widened seam in `lean/Shell/`, with a proof-relevant property: the package builds and R4's differential still passes unchanged. (D2) A node dispatcher and application outside `lean/Spec` and `lean/Ref` — a queue that retains pledged deliveries in memory for the process's lifetime, and sequential fetch by a reconnecting subscriber. (D3) A CloudEvents codec in the application tree, structured and binary modes. (D4) A narration mode emitting beside each protocol answer the verdict, condition, class and the rule in words. (D5) The demo: `scripts/run-node-demo.sh`, its transcript committed as `tests/contracts/node-demo-transcript.ndjson`, and the gate `tests/contracts/r5_node_demo.sh`.

**Acceptance, each mechanically checkable.** `bash scripts/run-node-demo.sh` exits zero and reproduces the committed transcript byte for byte; the transcript contains a publish, a fetch by a reconnected subscriber, the queue's credit gating one delivery, and both CloudEvents content modes round-tripping their attributes; the gate's **mutation** is one non-conforming frame — a `flow` whose `delivery-count` is not this endpoint's last known, the shape `exchange-flow-receiver-count-not-echoed` already pins — refused with `amqp:invalid-field`/`malformed` and the rule named in the narration; `bash tests/contracts/s1_differential.sh`, `s3_exchanges.sh` and `s4_flow.sh` still pass; **`bash tests/contracts/r4_wire_differential.sh` passes after D1 with the same per-vector report it gives before the migration, which is D1's proof** — it is the only check that builds `amqp-wire-app`, drives it over a socket and asserts its per-vector report, so without it D1's promise is unmeasured; the package builds as the repository's own clause does, `(cd lean && LAKE_NO_CACHE=1 lake build)` under the pinned shell, because a root-relative `lake build` fails with `no configuration file`; and no module under `lean/Impl` imports the boundary. The earlier criterion "the trust gate's printed count is unchanged" is **withdrawn**: that gate prints the count by design rather than comparing it to a baseline, so it could not check what the criterion claimed.

**Non-goals.** No broker: no durability, no routing language, no address grammar beyond what CloudEvents' binding and the demo need, no TLS, no SASL over the socket, no live fan-out. No performance claim, no new proof, and no rule invented where CloudEvents or this specification already states one — where neither does, the demo says so, and the `out-of-scope: node-and-filter-behaviour` clauses remain the record of that boundary.

**Provenance of this scope.** A reviewer found three things in the first version: that the sequential shape cannot retain node state through an `App` that is a pure function of the core's state and a `serveConn` that returns only it; that its description of the binding's two content modes was wrong in the placement of binary attributes and in the conditionality of JSON support, and that the binding's own dependencies were unpinned; and that the acceptance criteria named neither scripts nor a mutation and claimed a check the trust gate does not perform. All three are answered above rather than left to be discovered while building. A second review found the answers wrong in three more places: the `σ = Unit` claim conflated semantic equivalence with an unchanged interface; the acceptance list omitted the one gate that measures D1's promise while the section promised it; and the package-build command was written root-relative where the configuration is under `lean/`.

## The server's remaining obligations: what is a gap and what is the standard's boundary

§23.2 settles how a server *runs* — one proved core per connection, the dispatcher inside the unproved shell. This is the other axis: what a server must *do* that the
specification does not yet state or enforce. **Counts are deliberately absent and each category points at the record that carries them**, because those records move and this
section would then be asserting a number that had gone stale.

**1. Terminus behaviour is the standard's own boundary, not a gap in this work.** `source`/`target` semantics, routing, queues, filters, `dynamic` and `node-properties` are
declared `out-of-scope: node-and-filter-behaviour` and `out-of-scope: container-node-topology` in the dispositions, and §3's non-goal says the same in prose: *AMQP core defines
links and termini, not what a destination does with a message.* A specification that added routing would be specifying something else. A server implementer brings this from
elsewhere, and that is the standard's division rather than an omission here.

**2. The model's restrictions, which a server meets on its first day.** §13's D4 record keeps `MODEL RESTRICTION: the S4 slice contains at most one link per session` and
classifies the clauses it touches as fully modelled, vacuous under the restriction, or deferred until a registry exists, with four named triggers that would widen it. What a
server feels through it: **one delivery in progress, no link identity, no unsettled map, and no reattach or resume** — so **resumption, which is how a server survives a client
reconnecting, is not modelled at all**, nor are interleaved deliveries on distinct links (`ledger/ambiguities/interleaved-deliveries-absorbed.json`) nor duplicate link names at
one node (`ledger/ambiguities/link-uniqueness-vacuous.json`). *Multiple sessions per connection are modelled*: the connection maps incoming frames to sessions by channel. This
is the largest thing a server needs and does not have, and it is a recorded decision with named widening triggers rather than an oversight.

**3. Obligations the standard places on any peer that the model does not yet enforce.** The ledger's `deferred:` dispositions are the coverage record, concentrated in S5 (the
message layer — sections, annotations, outcomes), then S4, S3-session, S6 (transactions) and S7-SASL. **The live and named list for an implementer is the ledger itself.**
For the widening's harness-reachable obligations, the failure-first family is now carried by the generator in `vectors/generated-exchanges.ndjson`: each vector records the
clause obligation, the register's reading, and the failing step both artefacts exhibited before implementation. `vectors/isolation.md` says what each vector's experiment
witnessed. Read those records rather than a summary of them, this one included.

**4. Time, which the model does not have.** `open.idle-time-out` is the one Part 2 obligation whose subject is a clock, and it is treated as `environment:
implementation-idle-policy` rather than as a rule: the conformance interface carries an opaque `tick` input (`lean/Contracts/Conformance.lean`) and **nothing in the semantics
consumes it**. A server is the peer that must actually drop a silent connection, so this is the first gap a server implementer meets — and unlike category 2 it is not a decision
awaiting a trigger, it is the boundary of what a step relation over frames can state.

**5. Host-level assumptions a server leans on harder than a client.** `environment: server-hostname-default`, the TLS and SNI boundary entries, `tcp-ordered-stream` and
`tcp-close-order`: assumptions about the host, recorded as assumptions, and the ones a listener depends on most. They sit in the ledger beside the clause they qualify, which is
where an implementer should look rather than here.
